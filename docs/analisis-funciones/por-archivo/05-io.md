# io/ — documentación por archivo

## `io/src/main.c` (192 líneas)

Punto de entrada del módulo. Arma el boot logger, carga config, valida y parsea el tipo de dispositivo (`argv[2]`), conecta con Kernel Scheduler, y entra en el loop de atención según el tipo. Es el único archivo del módulo con lógica de negocio real — el resto son helpers de infraestructura (config/logger/conexión).

### `int main(int argc, char** argv)`

Qué hace y cómo, paso a paso:

1. `io_boot_logger_create()` — crea un logger temporal (`logs/io_boot.log`) para poder loguear errores incluso antes de tener la config cargada (que trae el `LOG_LEVEL` real).
2. Valida `argc != 3` — el binario espera exactamente `./bin/io [Archivo Config] [Tipo]`. Si falta un argumento, loguea error y sale con `EXIT_FAILURE`.
3. `io_config_create(argv[1], boot_logger)` — carga el `.cfg`. Si falla (archivo inválido o propiedades faltantes), destruye el boot logger y sale.
4. Parsea `argv[2]` con una cadena de `strcmp` contra `"STDIN"`, `"STDOUT"`, `"SLEEP"` para setear `t_tipo_dispositivo_io tipo_dispositivo`. Si no matchea ninguno, loguea error, libera config y logger, y sale — este es el único chequeo de validez del tipo (no hay validación adicional en ningún otro punto del módulo).
5. Loguea la config (`io_config_log`), crea el logger definitivo (`io_logger_create`, con el `LOG_LEVEL` real del `.cfg`), destruye el boot logger.
6. `conectar_a_kernel_scheduler(...)` — abre el socket hacia el KS y hace el handshake (ver `conexiones.c`). El resultado (`socket_ks`) puede ser `-1` si la conexión falla; **no se valida ese `-1` acá** — si falla, el flujo sigue igual y el primer `recv` sobre un fd `-1` fallará silenciosamente devolviendo `-1` (que corta el `while` de cada rama del switch sin loguear la causa raíz de la desconexión).
7. Arma `t_io io = { .tipo_dispositivo, .socket_kernel = socket_ks }` — nota: el campo `.logger` de `t_io` (declarado en `io_tools.h`) **nunca se asigna ni se lee**; todo el código usa la variable local `logger`, no `io.logger`. Es un campo muerto de la struct.
8. `switch (io.tipo_dispositivo)` — un loop bloqueante por rama, documentado abajo. Cada rama es esencialmente el "programa completo" de ese tipo de dispositivo: no hay forma de que un mismo proceso `io` atienda más de un tipo a la vez.
9. Al cortarse el loop (el KS cierra la conexión o `recv` devuelve `<=0`), libera logger y config y retorna `EXIT_SUCCESS`.

Dónde se usa: es `main`, entry point del binario `bin/io`. Quien lo "usa" es el script de arranque del TP (fuera del alcance de este análisis) y, del lado remoto, `kernel_scheduler/src/conexiones/conexiones.c` (que acepta la conexión) y `kernel_scheduler/src/planificador/planificador.c` (que orquesta el protocolo real vía `io_enviar_pid_y_param`/`io_esperar_ok`/`hilo_ejecutar_io` — documentado en el doc de kernel_scheduler, no acá).

Para qué: es el simulador standalone de un dispositivo de E/S — mismo binario, tres roles posibles, elegidos en tiempo de arranque.

#### Rama `case STDIN` (líneas 80-115)

Qué hace y cómo: loop `while (recv(pid) > 0)`. Por cada iteración:
- Recibe `pid` (4 bytes) y `tamanio` (4 bytes) — el tamaño del buffer que el proceso simulado espera leer de teclado.
- Loguea inicio de IO y el pedido de `tamanio` caracteres.
- `malloc(tamanio)` para el buffer de entrada.
- Lee de la **entrada estándar real del proceso `io`** con `getchar()` carácter por carácter hasta `\n` o `EOF`, contando `bytes_leidos` sin importar si excede `tamanio` (pero solo escribe en `buffer` mientras `bytes_leidos < tamanio`, evitando overflow).
- Si el usuario tipeó menos caracteres que `tamanio`, rellena el resto del buffer con `'\0'` (líneas 104-107) — así el buffer siempre queda del tamaño exacto pedido, sin importar cuánto tipeó el usuario.
- `send(buffer, tamanio)` — devuelve el buffer completo al KS. **No hay un `MENSAJE_OK` separado**: el contenido mismo, ya del tamaño esperado, es la confirmación de fin de IO (a diferencia de STDOUT/SLEEP).
- Loguea fin de IO.

Dónde se usa: recibido por `hilo_ejecutar_io` en `planificador.c` (rama STDIN, línea ~1240), que espera exactamente este contrato (dos `send` de 4 bytes salientes, un `recv` de `tamanio` bytes entrante, sin código de resultado).

Para qué: simula la syscall `STDIN` del ISA del proceso de usuario — leer del teclado real de la máquina que corre el proceso `io` tipo STDIN.

#### Rama `case STDOUT` (líneas 117-157)

Qué hace y cómo: mismo esqueleto de loop. Por iteración:
- Recibe `pid` y `tamanio`.
- `malloc(tamanio + 1)` (el `+1` es para el terminador nulo manual).
- `recv(buffer, tamanio, MSG_WAITALL)` — trae el contenido a imprimir.
- `buffer[tamanio] = '\0'` — termina el string manualmente (el contenido recibido no viene necesariamente null-terminated).
- `printf("%s", buffer)` + `fflush(stdout)` — imprime por la consola real del proceso `io`.
- Loguea el contenido impreso también en el log (`## PID: %u - %s`).
- **Sí** envía `MENSAJE_OK` (un `t_codigo_mensaje`, 4 bytes) al final — a diferencia de STDIN, acá el contenido no sirve como confirmación (ya fue recibido, no enviado), así que hace falta un mensaje explícito de "terminé".

Dónde se usa: `hilo_ejecutar_io` rama STDOUT en `planificador.c` (~línea 1248): manda pid+tamanio+contenido, después espera `io_esperar_ok`.

Para qué: simula la syscall `STDOUT` — imprimir contenido de memoria del proceso por la salida estándar real de la máquina que corre el `io` tipo STDOUT.

#### Rama `case SLEEP` (líneas 159-178)

Qué hace y cómo: recibe `pid` y `tiempo_ms`, hace `usleep(tiempo_ms * 1000)` (conversión ms→µs), y responde `MENSAJE_OK`. Es la rama más simple: no hay entrada/salida real, solo espera.

Dónde se usa: `hilo_ejecutar_io` rama SLEEP en `planificador.c` (~línea 1257).

Para qué: simula la syscall `SLEEP` del proceso de usuario — bloquear el proceso simulado por un tiempo fijo.

#### Rama `default` (líneas 180-186)

Defensiva — nunca debería alcanzarse porque `argv[2]` ya fue validado antes del switch. Loguea error, libera recursos y sale con `EXIT_FAILURE`.

## `io/src/config/io_config.c` (51 líneas)

Carga y valida el archivo de configuración del módulo usando la librería `commons` de la cátedra.

### `static bool tiene_todas_las_propiedades(t_config* config)`
Qué hace: `AND` de tres `config_has_property` — exige que existan `LOG_LEVEL`, `IP_KERNEL_SCHEDULER`, `PORT_KERNEL_SCHEDULER`. No exige nada más (no hay parámetro de nombre/id propio del `io`, ese viene por `argv`, no por config).
Dónde se usa: solo dentro de `io_config_create` (línea 19), es `static` — no se exporta.
Para qué: gate de validación antes de intentar leer valores, evita `config_get_string_value` sobre claves inexistentes.

### `t_io_config* io_config_create(char* path, t_log* logger)`
Qué hace y cómo: `config_create(path)` (de commons) → si es `NULL` (archivo no existe/mal formado) loguea y devuelve `NULL`. Si existe, valida con `tiene_todas_las_propiedades`; si falta alguna, destruye el `t_config` y devuelve `NULL`. Si todo está, hace `malloc` de `t_io_config` y copia (con `strdup`, para no depender de la memoria interna de `t_config`) los tres valores. Destruye el `t_config` de commons (ya no lo necesita, los valores están copiados) y devuelve el struct propio.
Dónde se usa: `io/src/main.c:31`.
Para qué: aislar el resto del programa de la librería `commons/config` — el resto del código solo ve un `t_io_config` con campos ya tipados como `char*`.

### `void io_config_log(t_io_config* config, t_log* logger)`
Qué hace: cuatro `log_info` imprimiendo cada parámetro cargado.
Dónde se usa: `io/src/main.c:53`.
Para qué: dejar constancia en el log de boot de qué configuración efectivamente se usó (debug/auditoría).

### `void io_config_destroy(t_io_config* config)`
Qué hace: chequeo de `NULL`, libera los tres `char*` (`strdup`s) y el struct.
Dónde se usa: `io/src/main.c` en cada uno de los 4 puntos de salida temprana (líneas 47, 58) y al final del programa (línea 189).
Para qué: evitar leaks de las tres cadenas duplicadas por `io_config_create`.

## `io/src/logger/io_logger.c` (19 líneas)

Dos funciones, ambas wrappers directos de `log_create` de `commons/log`.

### `t_log* io_boot_logger_create(void)`
Qué hace: crea un logger fijo a `logs/io_boot.log`, con tag `"IO_BOOT"`, salida por consola habilitada (`true`), nivel fijo `LOG_LEVEL_INFO` (no depende de config, porque se usa *antes* de tener la config cargada).
Dónde se usa: `io/src/main.c:14`.
Para qué: poder loguear errores de carga de configuración (el chicken-and-egg de necesitar loguear antes de saber el `LOG_LEVEL` real).

### `t_log* io_logger_create(t_io_config* config)`
Qué hace: igual que el anterior pero a `logs/io.log`, tag `"IO"`, y el nivel viene de `log_level_from_string(config->log_level)` — ya configurable.
Dónde se usa: `io/src/main.c:55`.
Para qué: logger definitivo de toda la vida del proceso, una vez que la config está validada.

## `io/src/conexiones/conexiones.c` (30 líneas)

### `#define HANDSHAKE_IO 2`
Redefine localmente el mismo valor que ya existe en `utils/src/utils/protocolo.h:9` (`#define HANDSHAKE_IO 2`). Este archivo **no incluye `protocolo.h`**, así que no hay conflicto de compilación, pero es una duplicación de la constante del contrato compartido — ver hallazgo abajo.

### `int conectar_a_kernel_scheduler(const char* ip, const char* puerto, const char* nombre_interfaz, t_log* logger)`
Qué hace y cómo, paso a paso:
1. `crear_conexion(ip, puerto)` (de `utils/sockets.c`) — conecta como cliente al KS. Si devuelve `-1`, loguea error y devuelve `-1` sin hacer handshake.
2. Envía el handshake: un `int32_t` con valor `HANDSHAKE_IO` (2) — así el KS, al aceptar la conexión, sabe que este cliente es un `io`.
3. Envía la longitud del nombre de interfaz (`argv[2]`: `"STDIN"`, `"STDOUT"` o `"SLEEP"`) como `uint32_t`, y después el string en sí (sin `\0` — longitud-prefijado, no null-terminado).
4. Loguea éxito y devuelve el fd.

Dónde se usa: `io/src/main.c:68`. Del lado servidor, `kernel_scheduler/src/conexiones/conexiones.c:86` (`case HANDSHAKE_IO`) es quien recibe este handshake y a partir de ahí lee la longitud+nombre para registrar el dispositivo (`planificador_registrar_io`, en el módulo kernel_scheduler, no documentado acá).

Para qué: es el punto de entrada al sistema para cualquier instancia de `io` — sin esta conexión el proceso no puede recibir pedidos.

## `io/src/io/io_tools.h` (28 líneas)

Solo tipos, sin lógica.

- `t_tipo_dispositivo_io` (enum): `SLEEP`, `STDIN`, `STDOUT` — nótese el orden (`SLEEP=0`, `STDIN=1`, `STDOUT=2`), distinto del orden en que aparecen en el enunciado/el `switch` de `main.c` (STDIN/STDOUT/SLEEP); no tiene impacto funcional porque el switch compara por nombre de rama, no por valor numérico, pero es una asimetría cosmética entre el orden de declaración y el orden de uso.

## Hallazgos notables

1. **`t_io.logger` es un campo muerto.** Se declara en `io_tools.h:25` pero `main.c` nunca lo asigna (la struct se inicializa solo con `.tipo_dispositivo` y `.socket_kernel`) ni lo lee — todo el módulo usa la variable local `logger` en su lugar. Confirmado con `grep -n "io\.logger\|io->logger" io/src/*.c io/src/**/*.c` sin resultados.
2. **`HANDSHAKE_IO` está duplicado.** `io/src/conexiones/conexiones.c:9` define su propio `#define HANDSHAKE_IO 2` en vez de incluir `utils/protocolo.h` y usar la constante compartida que ya existe ahí con el mismo nombre y valor (`utils/src/utils/protocolo.h:9`). Mismo patrón no se repite en `cpu/` (que si bien no fue objeto de este documento, vale como referencia): ahí sí se usa el handshake del header compartido. No es un bug (el valor coincide), pero es una inconsistencia de estilo/mantenibilidad — si alguna vez cambia el valor en `protocolo.h`, este archivo queda desincronizado silenciosamente.
3. **No se valida el resultado de `conectar_a_kernel_scheduler` en `main.c`.** Si la conexión falla (`-1`), el programa sigue igual hasta el primer `recv` sobre un fd inválido, que corta el loop sin mensaje de error específico sobre la causa (se ve como si el KS hubiera cerrado la conexión, no como "nunca until conectó").
4. El orden del enum `t_tipo_dispositivo_io` (`SLEEP, STDIN, STDOUT`) no coincide con el orden de aparición en el `switch` de `main.c` ni con el orden típico del enunciado (STDIN, STDOUT, SLEEP) — cosmético, sin efecto funcional (confirmado: la comparación en `main.c` es por string, `strcmp` contra literales, no por el valor numérico del enum).
