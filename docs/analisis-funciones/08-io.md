# Módulo io — Análisis detallado

Interfaz de Entrada/Salida. Es un proceso standalone que se conecta al **Kernel
Scheduler** (KS) y simula un dispositivo físico de uno de tres tipos: `STDIN`
(lectura por teclado), `STDOUT` (impresión por pantalla) o `SLEEP` (dispositivo
temporizador). El tipo se fija **por argumento de arranque**, no por config: el
mismo binario `bin/io` sirve para los tres roles.

Todo el módulo son ~356 líneas repartidas en 5 archivos. No hay lógica
compleja: es un bucle de `recv`/`send` sobre un único socket contra el KS.

---

### `main.c`

Único archivo con lógica de negocio real; no delega a `io/io_tools.h` (que es
solo un header de tipos, sin funciones).

#### `main(int argc, char** argv)` — main.c:13
- **Qué hace:** punto de entrada. Valida argumentos, carga config, determina el
  tipo de dispositivo, conecta al KS y entra en el bucle de atención específico
  del tipo.
- **Dónde se usa:** entry point del binario `bin/io`, invocado por
  `scripts_modulos/io.sh` o directamente por `start_all.sh` con
  `bin/io config/io.cfg STDIN|STDOUT|SLEEP`.
- **Para qué:** levantar una instancia de dispositivo de E/S que el KS pueda
  reservar (`planificador_tomar_io_libre`) para procesos bloqueados en syscalls
  `IO`.
- **Cómo funciona:**
  1. Crea el boot logger, valida `argc != 3` (exige exactamente `[config] [tipo]`
     — el tipo llega **por argv[2]**, no por el `.cfg`).
  2. Carga `t_io_config` desde `argv[1]` (`io_config_create`).
  3. Parsea `argv[2]` a `t_tipo_dispositivo_io` con `strcmp` contra
     `"STDIN"`/`"STDOUT"`/`"SLEEP"` literal; cualquier otro valor es error fatal.
  4. Crea el logger definitivo y se conecta al KS con
     `conectar_a_kernel_scheduler(...)`, pasándole **el mismo string `argv[2]`**
     como `nombre_interfaz` — ese string es lo que el KS usa después para
     clasificar el tipo de IO en su handshake (ver `kernel_scheduler/src/conexiones/conexiones.c:100-104`).
  5. Arma un `t_io` local (`tipo_dispositivo`, `socket_kernel`) y entra a un
     `switch` con un bucle infinito **por tipo**, hasta que el KS cierre el
     socket (`recv` devuelve `<= 0`):
     - **`STDIN`**: recibe `pid` (4 bytes) y `tamanio` (4 bytes) del KS, loguea
       inicio, reserva un buffer de `tamanio` bytes, lee caracteres de
       `stdin` con `getchar()` hasta `\n`/`EOF` (trunca si excede `tamanio`,
       rellena con `\0` si sobra espacio), y devuelve el buffer completo al KS
       con `send` — **no manda un `MENSAJE_OK` aparte**, el propio contenido es
       la confirmación (así lo espera `hilo_ejecutar_io` en `planificador.c:1246-1254`,
       que hace `recv` directo del buffer sin pasar por `io_esperar_ok`).
     - **`STDOUT`**: recibe `pid` y `tamanio`, luego recibe `tamanio` bytes de
       contenido (`MSG_WAITALL`), lo imprime por `stdout` (`printf`+`fflush`) y
       lo loguea, y **sí** responde con `t_codigo_mensaje = MENSAJE_OK` — lo
       espera `io_esperar_ok` del lado KS.
     - **`SLEEP`**: recibe `pid` y `tiempo_ms`, hace `usleep(tiempo_ms * 1000)`
       (conversión ms→µs) y responde `MENSAJE_OK`.
     - `default`: caso imposible (el `switch` ya viene acotado por el parseo de
       argv), solo logueado como error defensivo.
  6. Al cortarse el socket, libera logger y config y termina.

  El protocolo de cada tipo (qué manda/espera exactamente) está definido de
  forma **implícita y acoplada** entre este `main.c` y
  `kernel_scheduler/src/planificador/planificador.c:1214-1259`
  (`io_enviar_pid_y_param`, `io_esperar_ok`, `hilo_ejecutar_io`) — no hay
  opcodes de mensaje distintos por operación, solo el orden de los `send`/`recv`
  crudos sobre los mismos 4 bytes (`pid`) + 4 bytes (`param`).

### `config/io_config.c` + `.h` — carga de configuración

Responsabilidad: leer el `.cfg` de la IO (`LOG_LEVEL`, `IP_KERNEL_SCHEDULER`,
`PORT_KERNEL_SCHEDULER`) a un struct `t_io_config`.

#### `tiene_todas_las_propiedades(t_config* config)` *(static)* — io_config.c:6
- **Qué hace:** `true` si el config tiene las 3 claves obligatorias.
- **Dónde se usa:** solo dentro de `io_config_create` (io_config.c:19). No es
  visible fuera del archivo (`static`).
- **Para qué:** falla rápido y con mensaje claro si falta una clave, antes de
  intentar leerla y crashear.
- **Cómo funciona:** tres `config_has_property` encadenados con `&&`.

#### `io_config_create(char* path, t_log* logger)` — io_config.c:12
- **Qué hace:** abre el archivo de config en `path`, valida claves, y arma un
  `t_io_config*` con los 3 valores como strings (`strdup`).
- **Dónde se usa:** `main.c:31`.
- **Para qué:** dar a `main` la IP/puerto del KS y el nivel de log sin
  hardcodear nada.
- **Cómo funciona:** `config_create` (de la librería `commons`) parsea el
  archivo; si falla o faltan propiedades, libera y devuelve `NULL` (chequeado
  por el caller). Nótese que `port_kernel_scheduler` se guarda como **string**
  (no `int`), porque `crear_conexion` de `utils/sockets` espera el puerto como
  texto para pasarlo a `getaddrinfo`.

#### `io_config_log(t_io_config* config, t_log* logger)` — io_config.c:35
- **Qué hace:** loguea los 3 valores cargados.
- **Dónde se usa:** `main.c:53`, inmediatamente después de cargar la config.
- **Para qué:** trazabilidad en el log de arranque (requisito típico de la
  consigna: "loguear los parámetros leídos").
- **Cómo funciona:** `log_info` directo por cada campo.

#### `io_config_destroy(t_io_config* config)` — io_config.c:42
- **Qué hace:** libera los 3 strings y el struct.
- **Dónde se usa:** `main.c` en cada rama de error temprana y al final del
  `main` (línea 189).
- **Para qué:** evitar leaks al terminar el proceso o abortar el arranque.
- **Cómo funciona:** `free` por campo + `free` del struct, con guard `NULL`.

### `logger/io_logger.c` + `.h`

#### `io_boot_logger_create(void)` — io_logger.c:3
- **Qué hace:** crea un logger fijo a `logs/io_boot.log`, tag `"IO_BOOT"`,
  nivel `INFO`, con consola habilitada (`true`).
- **Dónde se usa:** `main.c:14`, antes de tener la config cargada (por eso es
  un logger separado y con nivel fijo).
- **Para qué:** poder loguear errores de arranque (config inválida, etc.)
  incluso antes de saber qué `LOG_LEVEL` pidió el usuario.
- **Cómo funciona:** wrapper directo de `log_create` de `commons/log`.

#### `io_logger_create(t_io_config* config)` — io_logger.c:12
- **Qué hace:** crea el logger definitivo a `logs/io.log`, tag `"IO"`, con el
  nivel indicado en la config (`log_level_from_string`).
- **Dónde se usa:** `main.c:55`, una vez que la config ya está validada.
- **Para qué:** logger operativo real, respetando el `LOG_LEVEL` configurable
  por archivo.
- **Cómo funciona:** igual que el anterior pero traduciendo el string de
  config a `log_level_t` con `log_level_from_string`.

### `conexiones/conexiones.c` + `.h`

#### `conectar_a_kernel_scheduler(const char* ip, const char* puerto, const char* nombre_interfaz, t_log* logger)` — conexiones.c:11
- **Qué hace:** abre una conexión TCP cliente al KS, envía el handshake
  `HANDSHAKE_IO` (valor `2`, hardcodeado localmente con `#define`) y a
  continuación el **nombre de la interfaz** (longitud + string), que es
  literalmente `argv[2]` (`"STDIN"`/`"STDOUT"`/`"SLEEP"`).
- **Dónde se usa:** `main.c:68`, una sola vez al arrancar.
- **Para qué:** darse a conocer ante el KS como dispositivo IO de un tipo
  concreto, para que quede registrado en la lista de IOs disponibles del
  planificador (`planificador_registrar_io`, del lado KS, en
  `kernel_scheduler/src/conexiones/conexiones.c` tras recibir el handshake).
- **Cómo funciona:**
  1. `crear_conexion(ip, puerto)` (de `utils/sockets`) — conecta el socket.
  2. `send` de un `int32_t` con el código `2` (mismo valor que
     `HANDSHAKE_IO` del lado `kernel_scheduler/src/conexiones/conexiones.c`,
     coordinado por convención, no por un header compartido con nombre
     simbólico).
  3. `send` de `uint32_t nombre_len` + los `nombre_len` bytes del nombre
     (`argv[2]`, sin el `\0`).
  4. Devuelve el fd conectado, o `-1` si `crear_conexion` falló.

### `io/io_tools.h` — tipos compartidos del módulo (sin funciones)

- `t_tipo_dispositivo_io` (enum `SLEEP, STDIN, STDOUT`): tipo de dispositivo
  que representa esta instancia. Usado en `main.c` para el `switch` del bucle
  principal.
- `t_io` (struct `tipo_dispositivo`, `socket_kernel`, `logger`): estado del
  proceso IO. Solo se instancia una vez en `main.c:70`; el campo `logger` del
  struct queda sin usar en la práctica (`main.c` usa la variable local
  `logger`, no `io.logger`) — dato menor, no afecta funcionalidad.
